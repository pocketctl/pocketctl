  • 三种上下文模式：accumulate / last_only / explicit
  • 人机关卡是内建步骤，不是事后追加

4.1 任务模型

CREATE TABLE task_queue (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id  UUID NOT NULL,
    task_type     TEXT NOT NULL,              -- 'agent_run' | 'script' | 'human_gate'
    agent_type    TEXT,                       -- 'claude-code' | 'codex' | 'opencode'
    prompt        TEXT NOT NULL,
    context       JSONB DEFAULT '{}',
    priority      INT DEFAULT 0,              -- -10..10, 借鉴 PilotDeck 4 级分类
    target_daemon UUID,
    max_retries   INT DEFAULT 1,
    timeout_sec   INT DEFAULT 7200,
    status        TEXT DEFAULT 'pending',     -- pending|claimed|running|completed|failed|cancelled
    claimed_by    UUID, session_id TEXT,
    result        JSONB, error TEXT,
    depends_on    UUID[],                     -- DAG 依赖
    route_on      JSONB,                      -- 条件路由规则
    created_at    TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_task_queue_status ON task_queue(status, priority DESC, created_at);
CREATE INDEX idx_task_queue_depends ON task_queue USING GIN(depends_on);

4.4 Daemon 任务轮询（借鉴 Multica pollLoop）

func (d *Daemon) pollLoop(ctx context.Context) {
    sem := make(chan struct{}, d.cfg.MaxConcurrentTasks) // 默认 20
    for {
        for _, rid := range d.allRuntimeIDs() {
            sem <- struct{}{}
            task, _ := d.client.ClaimTask(ctx, rid)  // SKIP LOCKED
            if task != nil {
                go func(t *Task) { defer func() { <-sem }(); d.handleTask(ctx, t) }(task)
                break
            } else { <-sem }
        }
        select {
        case <-time.After(3 * time.Second):  // PollInterval
        case <-d.taskWakeup:                  // WS 唤醒，亚秒级响应
        case <-ctx.Done(): return
        }
    }
}

调研范围：Microsoft Azure Architecture Center、Beam.ai 生产级模式、Redis 编排指南、学术文献（AAAI/ICAPS/ACM）、开源框架实现

5.1 编排模式全景图 — 6 种生产级模式

综合 Microsoft Azure Architecture Center、Beam.ai 和 Redis 的官方指南，形成以下 6 种模式的完整对比：

模式协调方式路由机制核心优势最大风险月成本 (10万次)
1. 顺序管道
(Sequential Pipeline)		 线性链，Agent 依次处理 确定性预定义顺序 审计友好、阶段清晰 错误传播级联、无并行 $4,500/10万次
2. 扇出/扇入
(Fan-out/Fan-in)		 并行，聚合器合并 确定性或动态选择 延迟降低 75%、多视角 API 限流、状态竞态、聚合失真 $5,500/10万次
3. 编排器-工作者
(Orchestrator-Worker)		 中心编排器委派 编排器决策 单问责点、成本降 40-60% 单点故障、4+ 工作器时上下文溢出 $50,000/月（大规模）
4. 路由器/交接
(Router/Handoff)		 分类器选择专家，一次一个活跃 Agent 自行决定何时转移 最便宜（~1,200 tokens/次） 无限交接循环、上下文丢失累积 $1,200/10万次
5. 多 Agent 辩论
(Group Chat/Debate)		 共享对话线程、聊天管理器控制 管理器控制发言顺序 减少幻觉、多专家验证 对话循环、谄媚级联（多数派错误） 高（15+ LLM 调用/任务）
6. 自适应规划
(Magentic/Adaptive)		 管理器构建任务账本，动态调整 管理器动态分配和重排 开放问题的最优解 收敛慢、目标漂移、成本不可预测 最高且不可预测

5.3 各模式的失败模式（生产环境真实案例）

⚠️ 每个模式在特定条件下都会崩溃

模式如何失败缓解措施
编排器-工作者 编排器上下文窗口在 4+ 工作器时溢出；工作流测试成本 $0.50，生产 10 万次执行变 $50,000/月 限制工作器数量 ≤ 4；上下文压缩；使用显式模式（explicit context）
顺序管道 4 Agent 管道累积 950ms 协调开销，实际处理仅 500ms；3 Agent 管道消耗 29,000 tokens vs 单 Agent 10,000 管道 ≤ 3 个 Agent；每步验证输出质量
扇出/扇入 15 并发 Agent × 10 req/s = 150 req/s，API 限制 100；N Agent 有 N(N-1)/2 竞态（5 个=10，10 个=45） 限流器 + 信号量；聚合前验证一致性
多 Agent 辩论 谄媚级联：Agent 倾向同意多数派位置（错误共识）；5 轮 × 3 Agent = 15 次 LLM 调用，结果仍可自信地错误 ≤ 3 Agent；每轮独立评估；maker-checker 模式
交接/路由 无限循环：A→B→C→A；每次转移上下文损失累积 最大跳数限制；交接链审计；路由器用便宜模型
自适应规划 目标漂移：多轮迭代后计划偏离原始意图；回溯浪费所有分支计算 目标对齐检查；最大迭代限制；人工确认关键决策

5.4 反模式（Anti-Patterns）— 来自生产环境的教训

反模式描述解法
过早编排器
(Premature Orchestrator)		3 个工具 + 1 个用例，但建了 4 个专家 Agent。系统比单 Agent 更慢、更贵、更难调试单 Agent → 路由模式 → 管道 → 扇出 → 层级。逐步升级
上帝编排器
(God Orchestrator)		编排器有 3,000 token 系统提示，描述所有专家和规则。把单体提示问题移到了上一层编排器保持简单：分类请求 → 选择专家 → 交接。其他什么都不做
聊天网格
(Chatty Mesh)		8 Agent 全连接网格 → 28 条通信通道。Token 成本爆炸全网格限于 3-4 个紧密耦合 Agent；更大规模拆分为小组
框架陷阱
(Framework Trap)		在理解模式之前先选择了框架。代码被框架抽象锁定先用纯语言实现模式，只在真正需要时引入框架

5.5 算法选择决策矩阵

渐进式升级路径（90% 生产系统只需要前 2 步）

Step 1: 单 Agent + 分组工具 + 结构化输出
   ↓ (工具数 > 12 或请求类型显著分化)
Step 2: 路由器 + 专家（最便宜的多 Agent 模式，~1,200 tokens/次）
   ↓ (任务有自然阶段顺序)
Step 3: 顺序管道
   ↓ (独立子任务需要并行加速)
Step 4: 扇出/扇入
   ↓ (问题横跨多个领域且规模足够大)
Step 5: 层级编排

原则：跳过 Step 3-5，直到 Step 2 明确失败。
大多数生产 Agent 系统永远不会超过 Step 2 — 这是好工程的标志，不是局限。
你的症状推荐模式原因
Agent 中途忘记指令，上下文窗口已满顺序管道拆分工作为阶段，每个 Agent 获得全新的聚焦上下文
Agent 选错工具概率 > 30%路由器/交接每个专家只拥有所需工具，路由器选专家而非工具
子任务不依赖彼此但串行执行太慢扇出/扇入并行化独立工作，墙钟时间 = 最慢 Agent
单 Agent 无法容纳跨领域上下文层级编排上下文分布到各层级，无 Agent 需要全貌
以上都不是 — Agent 工作正常保持单 Agent优化提示、分组工具、添加结构化输出

5.6 Token 成本数学模型

多 Agent 系统不是多用 Token，是乘法 Token

模式计算总 Tokenvs 单 Agent
单 Agent baseline1,000 input1,0001×
顺序管道 (3 Agent)1K + 1.5K + 2K4,5004.5×
扇出 (3 Agent + 聚合)3×1K + 2.5K5,5005.5×

关键结论：路由器/交接模式是最经济的多 Agent 模式，仅 1.2× Token 开销。这也是为什么它是最常见的生产模式。

type Backend interface {
    Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}

type ExecOptions struct {
    Cwd string; Model string; SystemPrompt string
    MaxTurns int; Timeout time.Duration
    PermissionMode string; AllowedTools []string
    ResumeSessionID string; CustomArgs []string
}

type Session struct {
    Messages <-chan Message  // 流式
    Result   <-chan Result   // 最终
}

type Message struct {
    Type MessageType  // text|thinking|tool_use|tool_result|status|error|log
    Content, Tool, CallID, SessionID, AgentID string
    Input map[string]any; Output string
}

type Result struct {
    Status string  // completed|failed|aborted|timeout|cancelled
    Output, Error, SessionID string
    DurationMs int64; Usage map[string]TokenUsage
}

6.2 通信协议选择

场景协议理由
Daemon ↔ Relay 实时通信WebSocket (已有)双向低延迟
Relay 内部事件内存事件总线同步发布，注册顺序执行
多 Relay 节点Redis Streams (可选)仅在多节点时启用
Agent ↔ 外部工具MCP标准化工具上下文注入
跨平台互操作 (未来)A2A标准化跨厂商通信

7. 工作流编排

7.1 DAG 优先原则

  • 真正并行：无依赖节点同时执行（LLMCompiler 验证：3.6× 加速）
  • 条件路由：边携带谓词，根据输出动态选择下游路径
  • 部分故障恢复：失败节点只阻塞其下游子图，不影响其他分支
  • ⚠️ 关键判断：如果你的工作流大多数节点依赖直接前驱，你有一个"伪装成 DAG 的线性工作流"，并行化收益有限

8.3 安全架构 — 三层策略引擎（借鉴 AWS Cedar）

L1: Agent → Tool 权限检查       // 该 Agent 能否调用此工具？
    └─ DENY → 立即阻止
L2: Agent → Agent 委托检查      // 子 Agent 权限 ⊆ 父 Agent 权限
L3: 发起用户身份验证            // HMAC-SHA256 签名信封保证不可篡改

10. 技术选型建议

层次推荐理由
调度引擎TypeScript (Relay 内)与现有 Relay 一致，无需新服务
Daemon 重构Go (现有)exec.Command 天然优势
任务队列PostgreSQL SKIP LOCKED已有 PG，无需引入 Redis/Kafka
事件总线内存 EventEmitter（单节点）/ Redis Streams（多节点）渐进式复杂度
工作流定义YAML + JSON Schema可读、可版本控制、可 diff
WebSocketgorilla/websocket (已有)扩展消息类型即可
Web UIVue 3 + TypeScript (已有)扩展现有 dashboard

为什么不引入重量级依赖

  • 不用 Temporal/Prefect/Airflow：pocketctl 的工作流规模不需要分布式引擎。YAML + 内存执行器足够
  • 不用 Redis（默认）：PostgreSQL SKIP LOCKED 是最简任务队列方案。单节点无需消息队列
  • 不用 LangGraph/CrewAI：pocketctl 定位是控制平面，不是 Agent 运行时。调度逻辑自己写更精简
  • 不用 gRPC：WebSocket 已满足所有实时通信需求

📋 总结

一句话总结

pocketctl 已拥有 Agent 管理平台的全部核心基础设施。 借鉴 Multica 的 Backend 接口模式和 PilotDeck 的智能路由体系， 结合 6 种生产级编排模式的量化选型指南，用 10 周可构建出完整的 Agent 调度平台。

四个最重要的设计决策

  1. 不要构建 Agent Loop，包装它。（Multica）— 一个 Backend 接口，每种 CLI 一个文件
  2. DAG 优先，不是链。（Conductor + DAG-First）— 从第一天就支持并行和条件路由
  3. 从最简单的模式开始。（Beam.ai + Azure）— 路由器/交接覆盖 80% 场景，仅 1.2× Token 开销
  4. 确定性编排为主，LLM 编排为辅。— 已知结构用 YAML（零 Token）；探索性任务用 LLM
