Exit → Continue Session 内容同步修复方案 pocketctl relay · 2026-06-12

1. 背景知识

Claude Code 将 session 数据存在两个目录：

~/.claude/
├── sessions/              ← PID 级元数据（临时文件）
│   └── <pid>.json          仅记录 pid / sessionId / cwd / status
│                            exit 后 Claude Code 删除此文件
│
└── projects/              ← 对话内容持久存储
    └── -Users-xxx-myapp/
        └── <sessionId>.jsonl  所有对话轮次逐行存储
                               exit 后保留，continue 后追加写入

关键认知：exit 后再 continue，session ID 不变，JSONL 文件不变。 对 relay 来说这是同一个 session（DB 中同一行，靠 ON CONFLICT (session_id) DO UPDATE 更新状态）。

2. 问题现象

在终端中 /exit 退出 Claude Code，再 claude --continue 恢复对话后：

  • Web 客户端状态栏显示"已退出"，banner 不消失
  • 新对话内容可能无法同步显示
  • Session 状态永远停在 exited

3.2 三处断裂

#断裂点位置后果
① delete knownSessions[sessionId] watcher.go:192 handleRemovedFile 清除了 sessionId→file 的映射。
新 PID 文件创建时找不到已知记录，
触发 "discovered" 而非 "changed"
② return false 且不更新状态 manager.go:169 RegisterTerminalSession 对已存在的 terminal session
直接返回 false，不更新 PID、status、exit_reason
③ if !registered { break } main.go:743 handler 跳过 SetSessionStatus 调用，
没有任何 session_status 事件发到 relay

①②③ 叠加：

  • ① 是确定性 bug（每次都触发）——remove 必定删 map，create 必定找不到
  • ② 是防御不足——设计时没考虑 exit→continue 场景
  • ③ 是② 的直接后果——既然②返回了 false，③就什么都不做

4. 修复方案

4.1 整体策略

不引入新字段、不改数据结构、不增加 goroutine 管理复杂度。 纯收敛逻辑分支，让 exit→continue 的路径走对。

4.2 改动 1：watcher.go — 保留 knownSessions

📄 internal/watcher/watcher.go 1 行改动 
// No other file tracks this session — it's truly gone
@@ -191,7 +191,6 @@
     if sess, exists := sw.knownSessions[sessionId]; exists {
-        delete(sw.knownSessions, sessionId)
+        // Keep in knownSessions — the session may reappear via --continue
+        // with a new PID file but the same sessionId. knownSessions is
+        // per-daemon-process, so stale entries don't accumulate forever.
         sw.eventsCh <- SessionEvent{
             Action:   "removed",
             Session:  sess,

效果：新 PID 文件创建时，knownSessions[sessionId] 仍存在， 触发 "changed" 而非 "discovered"。 "changed" handler 会调用 SetSessionStatus 更新状态。

4.3 改动 2：manager.go — RegisterTerminalSession 更新已有 session

📄 internal/session/manager.go ~12 行改动 
// RegisterTerminalSession registers a session discovered from the terminal.
-// Returns true if newly registered or upgraded from daemon→terminal (teller should start).
-// Returns false if already a terminal session (skip).
+// Returns true if a tailer should be started (new session or daemon→terminal upgrade).
+// For existing terminal sessions (--continue), updates PID/status and returns false.
 func (sm *SessionManager) RegisterTerminalSession(sessionID, cwd string,
     pid int, ttyPath string, status string) bool {
     sm.mu.Lock()
     defer sm.mu.Unlock()

     if sm.childPids[pid] {
         return false
     }

     if ps, ok := sm.sessions[sessionID]; ok {
         if ps.Source == "terminal" {
-            // Already a terminal session — skip
-            return false
+            // Re-discovered (e.g. --continue): update PID, status, cwd
+            ps.Pid = pid
+            ps.Status = status
+            ps.ExitReason = ""
+            if cwd != "" { ps.Cwd = cwd }
+            if ttyPath != "" { ps.TTY = ttyPath }
+            return false // no new tailer needed — old one works on same JSONL file
         }
         // Daemon-created session appeared in watcher — user resumed in terminal.
         ps.Source = "terminal"
         ps.Pid = pid
         if cwd != "" { ps.Cwd = cwd }
         ps.Status = status
         if ttyPath != "" { ps.TTY = ttyPath }
         return true
     }

     // ... new session logic unchanged ...
 }

效果：即使走了 "discovered" 路径，内存中的 PID、status、ExitReason 也会被正确更新。

4.4 改动 3：main.go — discovered 分支发出 session_status

📄 cmd/pocketctl/main.go ~5 行改动

-        logger.Debug("session already known, skipping tailer", ...)
+        // Re-discovered (e.g. --continue): tailer already running on same JSONL,

效果：改动 1 生效后，这个分支通常不会走到（走了 "changed"）。 但作为安全网，万一某些边缘情况仍触发 "discovered"，这里也会正确更新状态。

7. 风险与注意事项

  • 不引入新字段：不修改 ProcessState 结构体，零 API 变更
  • 不改变 goroutine 生命周期：旧 tailer 继续工作（同 inode 同 offset），不会出现双 tailer 竞争
  • knownSessions 不删不会泄露：这是个进程内 map，daemon 进程最多几十个条目，进程退出即释放
  • 改动 2 和 3 是安全网：即使改动 1 因某种原因不生效，改动 2+3 也能保证状态更新
  • 需要测试的场景：
    • 正常 exit → continue（最常见）
    • 进程 crash 后 continue
    • 多次 exit → 多次 continue
    • 两个不同 session 交替 exit/continue
  • 不涉及的场景：JSONL 文件被手动删除、daemon 重启期间 continue（会走 scanExisting，需单独验证）
