pocketctl × OpenClaw 接入方向讨论

2026-06-26 · 头脑风暴 · 方向探讨

1. 背景

pocketctl 目前接管 Claude Code、Codex、OpenCode 三个 agent 的 session 监控与管理。 OpenClaw 是一个自托管的 AI 助手网关，具备多 agent 编排能力和 20+ 消息通道（飞书、Discord、Telegram 等）接入能力。

pocketctl 核心资产

  • JSONL 实时流解析
  • PTY 会话控制（/compact, /effort, 中断）
  • PreToolUse 审批卡片（web + iOS）
  • Token 分维度分析
  • Host 资源监控
  • iOS 原生 App

OpenClaw 核心资产

  • 多 agent 编排调度
  • 20+ 消息通道（飞书/Discord/微信…）
  • Gateway 架构
  • Agent 路由
  • 自托管、隐私优先

2. 讨论过程

2.1 第一轮：接入模式

三种可能的接入关系：

  1. OpenClaw 作为被监控的 agent — 类似现在的 claude/codex，发现 + 监控 session
  2. OpenClaw 作为 session 数据源 — 通过 API 读取 OpenClaw 已有 session 列表
  3. 深度集成 / 能力互补 — pocketctl 触发 OpenClaw 的 agent 能力，或 OpenClaw 通知集成

结论：选方向 3，但不是"发起任务"，而是把 OpenClaw 作为编排层 — 用户选择 OpenClaw + 指定多个底层 agent，利用其多 agent 协作能力。

2.2 第二轮：Session 粒度

OpenClaw 驱动多个 agent 时，内部可能包含多个子 agent 调用：

  • 粗粒度：只看 OpenClaw 一层，显示"正在让 Claude Code 写代码"
  • 细粒度：展开内部，看到每个子 agent 的独立时间线、消息流、token 消耗

2.3 第三轮：结合飞书通道的优势

OpenClaw 已实现飞书/Discord 远程 chat，但经分析发现飞书通道存在硬伤（见 §3）。最终定位：

核心定位：OpenClaw 管"入口"和"编排"，pocketctl 管"过程"和"审批"——互为补充，不是替代。

3. OpenClaw + 飞书做不好的事

🔎 2026-06-26 联网核实修正

核对 OpenClaw 官方文档与官方飞书插件（larksuite/openclaw-lark，production-ready，WebSocket + webhook）后， 原 §3 有两条论断已过时/不准确，下面就地标注修正：

  • 飞书插件已支持流式输出（卡片内实时刷新文本 + Thinking/Generating/Complete 状态）→ §3.1 不是"不可见"，而是"只到文本层"。
  • 飞书插件已支持敏感操作确认按钮 → §3.2 不是"审批做不到"，而是"富审批（命令全文 / 风险分级 / diff / 改参再批 / 逐 hook 粒度）做不到"。
  • OpenClaw 本身也是自托管（历史以 markdown/yaml 存 ~/.openclaw），且自带 Web Control UI（含 session 监控）+ iOS/Android mobile nodes → 与 pocketctl 有重叠，差异点必须落在"深度 / 控制 / 分析"而非"有没有"。

§3.3 / §3.4 / §3.5 经核实仍然成立；§4 已按核实结果重写。

3.1 流式有了，但只到"文本层" 已修正

原判断已修正：官方飞书插件已支持流式（卡片内实时刷新 assistant 文本 + Thinking/Generating/Complete 状态）。真正的差距在深度——飞书流的是 agent 的文本回复， 不是底层 JSONL 事件流。仍然看不到：

  • 每个 tool call 的完整 input/output（命令全文 / 可能几百行代码）
  • thinking 原始内容、token usage 等结构化事件
  • Sub-agent 的内部活动与独立时间线

看得到"它在说什么"，看不到"它具体在执行什么"。

3.2 "确认按钮"有了，但富审批做不到 已修正

原判断已修正：飞书插件已支持"敏感操作确认按钮"，generic 的 approve/deny 能做。 但 pocketctl 的 PreToolUse 富审批仍是飞书接不住的：

  • 展示完整命令内容和风险分级（不是一句"是否执行敏感操作"）
  • 渲染将要写入的代码 diff 再决定
  • 用户改参数再 approve（modify-then-approve）
  • 逐 PreToolUse hook 粒度拦截，而非整轮一个确认

pocketctl 近期提交：0d47a29 feat(approval): PreToolUse 审批代理 — daemon hook 代理 + web/iOS 审批卡片

3.3 多 Session 并行的混乱

用户从飞书发了 3 个任务 → 3 个 agent 同时跑。飞书里三个 session 的消息全部交织在同一个频道， 完全分不清谁是谁。pocketctl 有独立的 session 列表、状态、重命名、置顶。

3.4 PTY 级别的直接操控

通过 PTY 向 agent 进程发送控制序列：

  • /compact 上下文压缩
  • /effort 动态调整思考深度
  • 切换 permission mode（default → acceptEdits → plan）
  • 中断正在运行的 session（Ctrl+C）

OpenClaw 通过飞书无法传递这些 PTY 操作。

3.5 Token 分析与成本追踪

按天/模型/host 的分维度 token 消耗，需要持续采集 JSONL 中的 usage 数据并聚合。飞书不是数据分析工具。

4. 核实后仍站得住的差异化用户场景

已按 OpenClaw + 官方飞书插件最新版核实 前提先讲清：OpenClaw + 飞书已经能做流式输出、敏感操作确认按钮、多 agent 隔离 session、 自带 Web/iOS 控制面。所以这里只保留两类差异点：①"飞书做了但做不到位（深度差）"，②"OpenClaw 结构上根本不碰"。 每条都标了核实后的成色（强 / 中），文末单列已撤回的几条以示诚实。

4.1 PTY 级控制：中断 → 注入纠偏 → 续跑 成色：强

"我想让它停下、纠正一句话、再接着原 session跑；顺手 /compact 压一下上下文、/effort 调思考深度、切到 plan 模式。"
  • OpenClaw + 飞书：只路由消息给 agent，不驱动 agent 进程的 PTY；发条消息 ≠ 注入到正在跑的进程
  • pocketctl：PTY 级中断 + 注入 + 续跑 + /compact / /effort / 切 permission mode，外加 Git Worktree 隔离（520b2b9）做安全回退

这是 §3.4 的延伸，核实后最干净的护城河——OpenClaw 的能力边界止于消息收发。

4.2 PreToolUse 富审批 + 跨 session 审批队列 成色：强

"飞书弹了个'是否执行敏感操作'，可我想看命令全文 + 风险分级 + 要写入的 diff，还想改个参数再批；3 个 agent 同时卡着等我，我连还有几个在排队都不知道。"
  • OpenClaw + 飞书：有 generic 确认按钮，但无命令全文/风险分级/diff 渲染、无 modify-then-approve、无跨 session 审批队列与待办计数
  • pocketctl：逐 PreToolUse hook 富审批（0d47a29）+ 复用 DiffCard（45225d7）渲染改动 + 统一审批队列（待审计数 / 按风险排序 / 批量处理）

差异在深度与并发治理，不是"有没有审批"。

4.3 Token 多维分析 + 预算阈值熔断 成色：强

"一个失控 agent 一晚上烧了几百块 token，飞书只会让我事后自己心算，没人在阈值处拦一下、也没人告诉我钱花在哪个模型/host 上。"
  • OpenClaw + 飞书：聊天网关，不是数据工具，无 token 聚合 / 预算 / 熔断概念
  • pocketctl：已持续采集 JSONL usage，按天/模型/host 分维度聚合 + 趋势；可加预算阈值告警 → 触发暂停/中断该 session

4.4 JSONL 全事件深度可观测（含 sub-agent） 成色：中

"飞书能看到它在说什么，但看不到它具体执行了什么——某个 tool 的完整 input/output、sub-agent 在干嘛、它到底卡在哪一步。"
  • OpenClaw + 飞书：流的是 agent 文本回复（§3.1 已修正：流式是有的），但不暴露底层 JSONL 事件、tool 细节、sub-agent 内部时间线
  • pocketctl：JSONL 深度解析，每个 tool call 完整 input/output + thinking + sub-agent 独立时间线

4.5 agent 卡死 / 死循环主动告警 成色：中

"agent 在某个 tool 上反复重试、或 thinking 卡了十分钟，飞书一片安静，我以为它在干活，其实早僵住了。"
  • OpenClaw + 飞书："没新消息"无法区分"在思考"还是"卡死"，无停滞检测
  • pocketctl：daemon 持续解析 JSONL，可做停滞检测（无进展时长 / 重试循环）并主动推送告警

4.6 Host 资源监控（CPU / 内存 / 磁盘） 成色：中

"OpenClaw 把任务分到了几台机器跑，我想知道哪台 CPU 飙了 / 磁盘要满了——它有 node 概念，但不告诉我机器健康。"
  • OpenClaw + 飞书：有 Gateway / mobile node 概念，但不做主机资源监控
  • pocketctl：已有 Host 资源监控 + 多 Agent 适配器（520b2b9），session 天然带 host 归属与资源画像

4.7 敏感 output 不出本地（飞书 leg 仍进飞书云） 成色：中（已精确化）

"agent 跑部署脚本，.env / 密钥被当 tool output 转发进飞书，撤不回、同事都看到、飞书云端存了一份。"
  • 修正：OpenClaw 本身也是自托管（数据存 ~/.openclaw），所以泄露点不在 OpenClaw，而在飞书这一段传输——内容进了飞书（SaaS）云就不可控
  • pocketctl：敏感 output 可留在本地 daemon + 私有受控 UI，可脱敏、可按 host/session 隔离可见性，不必经飞书转发

表述要精确：这是"选择不把敏感内容推给飞书通道"的能力，不是"OpenClaw 会泄露"。

🗑️ 核实后已撤回 / 降级的论断（诚实记录）

  • "代码 diff 飞书完全看不了" → 降级并入 4.2：飞书卡片能贴富文本，只是没有 side-by-side diff / 改参再批，差在审批深度。
  • "断线后无法知道 agent 跑到哪" → 撤回：OpenClaw 有 session 历史 + Web Control UI 的 session 监控。残留价值只剩"重新接管 PTY 控制权"，已并入 4.1。
  • "Plan/Todo 无法原地刷新" → 撤回：飞书卡片支持原地刷新（流式就是证据），不成立。
  • "事后审计无从查起" → 降级：OpenClaw 把历史存成可 grep 的 markdown/yaml，不是查不到。残留价值只剩"step 级 tool-call 回放"，并入 4.4。

🎯 优先级建议（核实后）

按"差异最硬 + 复用成本最低"排序：4.2 富审批 + 队列（复用 DiffCard 45225d7 / 审批代理 0d47a29，几乎现成）> 4.1 PTY 控制（最干净的护城河，OpenClaw 结构上不碰）> 4.3 Token 分析 + 熔断（已有采集，加阈值即可）> 4.5 / 4.6 / 4.7 守护类。

5. 接入 OpenClaw 解锁的增量：新场景 × 新用户

2026-06-26 第二轮调研补充 前面几节是"防守视角"（pocketctl 比 OpenClaw+飞书强在哪）。这一节换"进攻视角"： pocketctl 现在只接管 coding agent（Claude Code / Codex / OpenCode），用户是终端里的开发者； 而 OpenClaw 本质是面向所有人的个人/团队 AI 助手网关。接它进来，是把 pocketctl 的场景边界和用户边界同时往外推。

5.0 四条边界，OpenClaw 把每条都往外推

边界pocketctl 现状（只接 coding agent）接入 OpenClaw 后的增量
Agent 类型编码 agent，观测单元 = 代码类 tool call+ 通用 agent：收发邮件、日历、文件、网页抓取、数据报表、智能家居…… 观测单元 = 任意 MCP / skill 动作
用户开发者（懂 terminal / JSONL）+ 运营 / 销售 / 客服 / PM / FinOps / 个人 & 家庭用户（不碰命令行）
入口本机终端启动+ 20+ 通道：飞书 / WhatsApp / Telegram / Slack / 微信生态…… 手机随时发起
信任自己写的代码+ 13,700+ 社区 skill（不可信、是攻击面）

每一条往外推，都对应一类新用户场景；而这些场景里 pocketctl 的"监控 / 审批 / 分析"资产恰好仍然适用——只是对象从代码换成了更广的动作。

5.1 审批从"approve bash"泛化到"approve 任意高危动作" 最大增量

coding agent 的危险动作是 rm -rf / 写文件；通用 agent 的危险动作是有现实副作用的：

  • 发邮件 / 发飞书消息给客户、对外发帖
  • 转账 / 下单 / 退款
  • 删日历事件、删云文档、改数据库
  • 开门锁 / 控制智能家居设备

pocketctl 的 PreToolUse 富审批（0d47a29）天然能拦这些——把"代码审批"升级成"AI 现实世界动作的人工闸门"。这是覆盖非开发者用户最直接的入口：运营不关心 diff，但一定关心"它要替我把这封邮件发出去了"。

5.2 不可信社区 skill 的安全护栏 供应链安全

"我装了个社区 skill 帮我抓数据，结果它在后台 curl 了一个陌生域名 / 读了我的 ~/.ssh。"

OpenClaw 生态有 13,700+ 社区 skill，约 65% 包着 MCP server，安全研究已把它称作新的攻击面（1Password："from magic to malware"）。 OpenClaw 核心只有 per-agent allow/deny 列表。pocketctl 能补上运行时护栏：

  • 逐 tool call 看到 skill 真正执行了什么命令 / 访问了什么网络与文件
  • 高危动作（外联未知域名、读敏感路径）实时拦截 + 审批
  • 事后审计：这个 skill 这次到底干了什么

这把 pocketctl 从"开发者效率工具"扩成"AI agent 供应链安全工具"——一个完全不同的卖点与用户群（安全 / 合规团队）。

5.3 给非开发者的"人话监督面板" 新用户群

"我是运营，不看 JSONL。我只想知道：我那几个 agent 现在在忙什么、今天替我花了多少钱、有没有在等我点确认。"
  • 现状面板：面向开发者——时间线 / token / tool 细节
  • 新增：面向非开发者的摘要视图——自然语言进度（"正在整理本周报表，3/5 完成"）、当日花费、待审批红点、一键 approve / 停止

同一套 daemon 数据，换一层"人话"呈现，用户范围从开发者扩到全员。

5.4 团队 / 多租户治理：补 OpenClaw 的核心空缺 企业市场

调研发现 OpenClaw 核心框架今天就缺：per-user 成本归属、审计追踪、配置变更审批、跨实例 skill 白名单、RBAC—— "none exist in core framework today"，且单租户、VM-per-user 过 30–50 人就崩。

pocketctl 已有的 token 多维分析 + 审计日志 + 审批代理 正好是这块拼图：

  • 按人 / agent / 通道的成本归属与配额（AI FinOps）
  • Auditor 只读视角：谁的 agent、什么时候、做了什么高危动作
  • 对外动作的审批路由（运营发起 → 主管审批）

新用户群：团队管理员 / 安全合规 / 财务 FinOps——从"个人开发者工具"迈进"企业治理"市场。

5.5 多通道入口的统一过程视图 跨通道

任务可能从飞书、WhatsApp、Telegram、Slack、微信生态任意通道发起。OpenClaw 负责"从哪进来"， pocketctl 提供与通道无关的统一过程面：不管你从哪个 App 丢的任务，都在一个地方看到"我所有 agent 此刻在干嘛"。

5.6 Lobster 多步工作流的展开与逐步审批 编排可观测

OpenClaw 的 Lobster 编排引擎支持多步 / 多 agent / sub-agent 委派，每步可换不同 agent、不同权限。 pocketctl 可把一条工作流展开成可视化 DAG，每步独立时间线 + 在关键步骤插入审批闸门，而不是只看到一句"工作流完成"。

🔌 技术枢纽：ACP —— 把 OpenClaw 启动的 coding session 接回 pocketctl

这也顺带回答了 §9 的"daemon 如何感知 OpenClaw 启动的 session"。核实 OpenClaw 文档：它通过 ACP（Agent Client Protocol）把 Claude Code / Codex / Gemini CLI 当受监督子进程跑，几个事实对接入很友好：

  • 跑在 host runtime、不在 OpenClaw 沙箱 → 和 pocketctl daemon 同主机，本来就看得见
  • 每个 harness 有独立 cwd 工作目录、Codex 用隔离 CODEX_HOME → coding agent 仍写自己的 JSONL，pocketctl 现有 tailer 可复用，但要按 cwd / CODEX_HOME 动态发现（不能只盯默认路径）
  • session id 形如 agent:<agentId>:acp:<uuid>、支持 session/load 续跑、过 gateway 重启不丢 → 可与 pocketctl 的 session 模型对齐
  • OpenClaw 暴露 /acp 控制：spawn / cancel / steer（注入指令不替换上下文）/ permissions 等

但有一个反转：ACP 是 JSON-RPC over stdio，不是 PTY。pocketctl 现在的 PTY 操控（/compact、Ctrl+C） 在 ACP 模式下未必直接适用——可能要走 OpenClaw 的 /acp 接口（cancel / steer / permissions）来实现等价控制。 接入的真正工作量在 "控制路径适配"，而非"看不看得到"。

⚠️ 一个必须正视的架构前提

pocketctl 现在的深度监控依赖 coding agent 的 JSONL。但 OpenClaw 的通用 agent（发邮件、抓网页那类） 并不产出 Claude Code 式 JSONL——要监控它们，pocketctl 得新增一条数据通路：消费 OpenClaw 自身的事件流 / API， 或在 MCP 工具调用层做拦截。§5.1–5.6 的非编码场景能否落地，取决于这条通路是否打通，这是接入的第一性技术决策。

💡 一句话重定位

只接 coding agent 时，pocketctl 是 "开发者的 agent 控制塔"； 接入 OpenClaw 后，它可以成为 "任何人、任何通道发起的 AI 动作的监控 · 审批 · 成本 · 安全中台"—— 场景从写代码扩到日常工作流，用户从开发者扩到全员与团队。

6. 放进真实赛道再看：远程续作的对手、边界与真正的拓宽点

2026-06-26 第三轮调研（结合"远程续作"产品 DNA） 先把 pocketctl 的核心讲准：它解决的是"人离开了 coding 机器，仍能用手机/网页继续推进工作"。 把这件事放进 2026 年的真实赛道看，结论会比 §5 更清醒——这块已经很挤，而且官方下场了。

6.1 现实检查：这个场景已被官方 + 一堆产品占住

玩家是什么远程能力缺口（= pocketctl × OpenClaw 的机会）
Claude Code Channels
Anthropic 官方		 把 Telegram/Discord/iMessage 消息发进运行中的 CC session（2026-03-20 研究预览） 只收发消息 核实：无审批系统 / 无 diff / 无审批队列 / 无 token 分析 / 无审计日志，只支持 CC + 3 通道、session 必须常驻
Codex Mobile（ChatGPT 内）
OpenAI 官方		 手机里直接跑/看 Codex 移动发起、查看 锁死 Codex / OpenAI 生态
CodeAgent Mobile
最像 pocketctl		 手机监督多家 coding agent（CC/Cursor/Codex/Copilot/Windsurf/Gemini/Aider…） approve diff、redirect tool call、终止失控、实时流、推送、跨设备续作、Team Spaces 无多通道聊天入口（单 agent 取向）、无深度团队治理、prompt/输出走自家云中转（非自托管）
AgentsRoom Mobile 手机监控 CC 推送、喂输入给卡住的 agent、approve 单 agent、无多通道、无治理
pocketctl（现状） 自托管 daemon + iOS/Web，深度监督 CC/Codex/(OpenCode) 审批 / diff / token / PTY 操控 / 审计 入口只有自家 App/Web、面向单个开发者、尚无多通道、尚无团队治理

两条必须正视的事实

  • 好消息：连 Anthropic 官方的 Channels 都只是"把消息发进 session"——无审批/diff/队列/token/审计。这验证了 pocketctl 的"深度"路线是对的，浅层聊天入口正在被商品化。
  • 坏消息："手机深度监督 coding agent"已经有 CodeAgent Mobile 这种近似克隆（approve diff / redirect / 推送 / 跨设备续作都有）。所以光有深度不够，pocketctl 正面单挑会拼成熟度。

6.2 因此：OpenClaw 不是用来"再做一个手机聊天 agent"

那块（手机里跟 agent 聊天）已被官方 Channels + CodeAgent 占住。OpenClaw 的正确用法，是去补所有对手都缺的三个空白—— 而这三个空白恰好是 OpenClaw 作为自托管 · 多通道 · 多租户网关的原生能力：

① 多通道入口

官方 Channels 锁 CC+3 通道；CodeAgent 是 app-only。OpenClaw 给 20+ 通道（飞书/WhatsApp/Telegram/微信生态…）。不用装新 App，从你已经在用的 IM 触达。

② 团队治理

CodeAgent 明确"无团队治理"，官方 Channels 是个人功能。OpenClaw 多 agent 多人共用一个 Gateway，pocketctl 叠上 RBAC/成本归属/审计（见 §5.4）。

③ 自托管 / 数据不出本地

CodeAgent 的 prompt 与输出过自家云中转。OpenClaw + pocketctl 都自托管——对"代码/输出不能进第三方 SaaS"的企业，这是直接的选型分水岭。

6.3 对齐 DNA 的三个真正拓宽点（都仍围绕"离开 coding 机器后继续工作"）

拓宽 WHO —— 从"单个开发者"到"团队 + 非开发利益相关者 + 不装 App 的人"

PM/创始人/客户从不坐在 coding 机器旁，但他们有飞书/微信。"功能做完没？""这步能上吗？"——OpenClaw 让他们从已有 IM 里问到进度、点审批；pocketctl 提供人话摘要与对外动作闸门。把 coding 工作的"远程参与者"从开发者扩到整条协作链。

拓宽 HOW（模态）—— 从"看屏幕点按钮"到"语音 / 电话发起"（真·离屏、免手）

核实：OpenClaw 支持语音条转写→当指令（含 slash 命令），并有 ClawdTalk/Vapi/Telnyx 电话呼入插件。开车/走路时口述"在家那台机子把这个 bug 修了"，回到有屏幕时用 pocketctl 审 diff。这是屏幕导向的对手（CodeAgent/Channels）覆盖不到的模态。

拓宽聚合 —— 跨 agent × 跨通道的"一个自托管深度面"

官方方案天然碎片化（CC 只连自己、Codex 只连自己）。OpenClaw 经 ACP 统一驱动 CC/Codex/OpenCode/Gemini，pocketctl 在其上做唯一的深度监督面——对抗"每个厂商一个孤岛 App"。这也正是 pocketctl 已接 CC/Codex、即将接 OpenCode 的延长线。

6.4 校准：别被 §5 的"广度"带偏 诚实提醒

§5 列了智能家居、通用邮件助手等很"宽"的场景。结合你的 DNA 再看：那些会把 pocketctl 推进 更挤、更不聚焦、且偏离"coding 远程续作"的战场（通用助手赛道还有 OpenClaw 自己、一堆大厂）。

建议的取舍：用 OpenClaw 拓宽 coding 续作的「人 / 模态 / 通道 / 部署形态」，而不要改变「做的是 coding 监督」这个内核。 §5.1（高危动作审批）、§5.2（不可信 skill 护栏）、§5.4（团队治理）与本节高度共振，优先； §5 里偏通用助手的部分，建议暂缓。

💡 第三轮一句话结论

"用手机监督 coding agent"已经被官方和 CodeAgent 占住，光做这个会卷。 接 OpenClaw 的意义不是多一个聊天入口，而是把 pocketctl 变成 "自托管 · 多通道 · 可治理"的团队级 coding 续作中枢—— 用对手都缺的三块（多通道 / 团队治理 / 不出本地）+ 语音离屏模态，去拓宽人和场景，但内核仍是 coding。

7. 核心洞察

💡 OpenClaw + 飞书 = 你能"跟 agent 聊天"，但无法"管理 agent 工作"

pocketctl 的价值不在于"发消息"（飞书已经做了），而在于 agent 跑起来之后的完整生命周期管理——实时监控、审批、控制、分析。
