pocketctl × OpenClaw 接入方向讨论

2026-06-26 · 头脑风暴 · 方向探讨

1. 背景

pocketctl 目前接管 Claude Code、Codex、OpenCode 三个 agent 的 session 监控与管理。 OpenClaw 是一个自托管的 AI 助手网关，具备多 agent 编排能力和 20+ 消息通道（飞书、Discord、Telegram 等）接入能力。

pocketctl 核心资产

  • JSONL 实时流解析
  • PTY 会话控制（/compact, /effort, 中断）
  • PreToolUse 审批卡片（web + iOS）
  • Token 分维度分析
  • Host 资源监控
  • iOS 原生 App

OpenClaw 核心资产

  • 多 agent 编排调度
  • 20+ 消息通道（飞书/Discord/微信…）
  • Gateway 架构
  • Agent 路由
  • 自托管、隐私优先

2. 讨论过程

2.1 第一轮：接入模式

三种可能的接入关系：

  1. OpenClaw 作为被监控的 agent — 类似现在的 claude/codex，发现 + 监控 session
  2. OpenClaw 作为 session 数据源 — 通过 API 读取 OpenClaw 已有 session 列表
  3. 深度集成 / 能力互补 — pocketctl 触发 OpenClaw 的 agent 能力，或 OpenClaw 通知集成

结论：选方向 3，但不是"发起任务"，而是把 OpenClaw 作为编排层 — 用户选择 OpenClaw + 指定多个底层 agent，利用其多 agent 协作能力。

2.2 第二轮：Session 粒度

OpenClaw 驱动多个 agent 时，内部可能包含多个子 agent 调用：

  • 粗粒度：只看 OpenClaw 一层，显示"正在让 Claude Code 写代码"
  • 细粒度：展开内部，看到每个子 agent 的独立时间线、消息流、token 消耗

2.3 第三轮：结合飞书通道的优势

OpenClaw 已实现飞书/Discord 远程 chat，但经分析发现飞书通道存在硬伤（见 §3）。最终定位：

核心定位：OpenClaw 管"入口"和"编排"，pocketctl 管"过程"和"审批"——互为补充，不是替代。

3. OpenClaw + 飞书做不好的事

🔎 2026-06-26 联网核实修正

核对 OpenClaw 官方文档与官方飞书插件（larksuite/openclaw-lark，production-ready，WebSocket + webhook）后， 原 §3 有两条论断已过时/不准确，下面就地标注修正：

  • 飞书插件已支持流式输出（卡片内实时刷新文本 + Thinking/Generating/Complete 状态）→ §3.1 不是"不可见"，而是"只到文本层"。
  • 飞书插件已支持敏感操作确认按钮 → §3.2 不是"审批做不到"，而是"富审批（命令全文 / 风险分级 / diff / 改参再批 / 逐 hook 粒度）做不到"。
  • OpenClaw 本身也是自托管（历史以 markdown/yaml 存 ~/.openclaw），且自带 Web Control UI（含 session 监控）+ iOS/Android mobile nodes → 与 pocketctl 有重叠，差异点必须落在"深度 / 控制 / 分析"而非"有没有"。

§3.3 / §3.4 / §3.5 经核实仍然成立；§4 已按核实结果重写。

3.1 流式有了，但只到"文本层" 已修正

原判断已修正：官方飞书插件已支持流式（卡片内实时刷新 assistant 文本 + Thinking/Generating/Complete 状态）。真正的差距在深度——飞书流的是 agent 的文本回复， 不是底层 JSONL 事件流。仍然看不到：

  • 每个 tool call 的完整 input/output（命令全文 / 可能几百行代码）
  • thinking 原始内容、token usage 等结构化事件
  • Sub-agent 的内部活动与独立时间线

看得到"它在说什么"，看不到"它具体在执行什么"。

3.2 "确认按钮"有了，但富审批做不到 已修正

原判断已修正：飞书插件已支持"敏感操作确认按钮"，generic 的 approve/deny 能做。 但 pocketctl 的 PreToolUse 富审批仍是飞书接不住的：

  • 展示完整命令内容和风险分级（不是一句"是否执行敏感操作"）
  • 渲染将要写入的代码 diff 再决定
  • 用户改参数再 approve（modify-then-approve）
  • 逐 PreToolUse hook 粒度拦截，而非整轮一个确认

pocketctl 近期提交：0d47a29 feat(approval): PreToolUse 审批代理 — daemon hook 代理 + web/iOS 审批卡片

3.3 多 Session 并行的混乱

用户从飞书发了 3 个任务 → 3 个 agent 同时跑。飞书里三个 session 的消息全部交织在同一个频道， 完全分不清谁是谁。pocketctl 有独立的 session 列表、状态、重命名、置顶。

3.4 PTY 级别的直接操控

通过 PTY 向 agent 进程发送控制序列：

  • /compact 上下文压缩
  • /effort 动态调整思考深度
  • 切换 permission mode（default → acceptEdits → plan）
  • 中断正在运行的 session（Ctrl+C）

OpenClaw 通过飞书无法传递这些 PTY 操作。

3.5 Token 分析与成本追踪

按天/模型/host 的分维度 token 消耗，需要持续采集 JSONL 中的 usage 数据并聚合。飞书不是数据分析工具。

4. 核实后仍站得住的差异化用户场景

已按 OpenClaw + 官方飞书插件最新版核实 前提先讲清：OpenClaw + 飞书已经能做流式输出、敏感操作确认按钮、多 agent 隔离 session、 自带 Web/iOS 控制面。所以这里只保留两类差异点：①"飞书做了但做不到位（深度差）"，②"OpenClaw 结构上根本不碰"。 每条都标了核实后的成色（强 / 中），文末单列已撤回的几条以示诚实。

4.1 PTY 级控制：中断 → 注入纠偏 → 续跑 成色：强

"我想让它停下、纠正一句话、再接着原 session跑；顺手 /compact 压一下上下文、/effort 调思考深度、切到 plan 模式。"
  • OpenClaw + 飞书：只路由消息给 agent，不驱动 agent 进程的 PTY；发条消息 ≠ 注入到正在跑的进程
  • pocketctl：PTY 级中断 + 注入 + 续跑 + /compact / /effort / 切 permission mode，外加 Git Worktree 隔离（520b2b9）做安全回退

这是 §3.4 的延伸，核实后最干净的护城河——OpenClaw 的能力边界止于消息收发。

4.2 PreToolUse 富审批 + 跨 session 审批队列 成色：强

"飞书弹了个'是否执行敏感操作'，可我想看命令全文 + 风险分级 + 要写入的 diff，还想改个参数再批；3 个 agent 同时卡着等我，我连还有几个在排队都不知道。"
  • OpenClaw + 飞书：有 generic 确认按钮，但无命令全文/风险分级/diff 渲染、无 modify-then-approve、无跨 session 审批队列与待办计数
  • pocketctl：逐 PreToolUse hook 富审批（0d47a29）+ 复用 DiffCard（45225d7）渲染改动 + 统一审批队列（待审计数 / 按风险排序 / 批量处理）

差异在深度与并发治理，不是"有没有审批"。

4.3 Token 多维分析 + 预算阈值熔断 成色：强

"一个失控 agent 一晚上烧了几百块 token，飞书只会让我事后自己心算，没人在阈值处拦一下、也没人告诉我钱花在哪个模型/host 上。"
  • OpenClaw + 飞书：聊天网关，不是数据工具，无 token 聚合 / 预算 / 熔断概念
  • pocketctl：已持续采集 JSONL usage，按天/模型/host 分维度聚合 + 趋势；可加预算阈值告警 → 触发暂停/中断该 session

4.4 JSONL 全事件深度可观测（含 sub-agent） 成色：中

"飞书能看到它在说什么，但看不到它具体执行了什么——某个 tool 的完整 input/output、sub-agent 在干嘛、它到底卡在哪一步。"
  • OpenClaw + 飞书：流的是 agent 文本回复（§3.1 已修正：流式是有的），但不暴露底层 JSONL 事件、tool 细节、sub-agent 内部时间线
  • pocketctl：JSONL 深度解析，每个 tool call 完整 input/output + thinking + sub-agent 独立时间线

4.5 agent 卡死 / 死循环主动告警 成色：中

"agent 在某个 tool 上反复重试、或 thinking 卡了十分钟，飞书一片安静，我以为它在干活，其实早僵住了。"
  • OpenClaw + 飞书："没新消息"无法区分"在思考"还是"卡死"，无停滞检测
  • pocketctl：daemon 持续解析 JSONL，可做停滞检测（无进展时长 / 重试循环）并主动推送告警

4.6 Host 资源监控（CPU / 内存 / 磁盘） 成色：中

"OpenClaw 把任务分到了几台机器跑，我想知道哪台 CPU 飙了 / 磁盘要满了——它有 node 概念，但不告诉我机器健康。"
  • OpenClaw + 飞书：有 Gateway / mobile node 概念，但不做主机资源监控
  • pocketctl：已有 Host 资源监控 + 多 Agent 适配器（520b2b9），session 天然带 host 归属与资源画像

4.7 敏感 output 不出本地（飞书 leg 仍进飞书云） 成色：中（已精确化）

"agent 跑部署脚本，.env / 密钥被当 tool output 转发进飞书，撤不回、同事都看到、飞书云端存了一份。"
  • 修正：OpenClaw 本身也是自托管（数据存 ~/.openclaw），所以泄露点不在 OpenClaw，而在飞书这一段传输——内容进了飞书（SaaS）云就不可控
  • pocketctl：敏感 output 可留在本地 daemon + 私有受控 UI，可脱敏、可按 host/session 隔离可见性，不必经飞书转发

表述要精确：这是"选择不把敏感内容推给飞书通道"的能力，不是"OpenClaw 会泄露"。

🗑️ 核实后已撤回 / 降级的论断（诚实记录）

  • "代码 diff 飞书完全看不了" → 降级并入 4.2：飞书卡片能贴富文本，只是没有 side-by-side diff / 改参再批，差在审批深度。
  • "断线后无法知道 agent 跑到哪" → 撤回：OpenClaw 有 session 历史 + Web Control UI 的 session 监控。残留价值只剩"重新接管 PTY 控制权"，已并入 4.1。
  • "Plan/Todo 无法原地刷新" → 撤回：飞书卡片支持原地刷新（流式就是证据），不成立。
  • "事后审计无从查起" → 降级：OpenClaw 把历史存成可 grep 的 markdown/yaml，不是查不到。残留价值只剩"step 级 tool-call 回放"，并入 4.4。

🎯 优先级建议（核实后）

按"差异最硬 + 复用成本最低"排序：4.2 富审批 + 队列（复用 DiffCard 45225d7 / 审批代理 0d47a29，几乎现成）> 4.1 PTY 控制（最干净的护城河，OpenClaw 结构上不碰）> 4.3 Token 分析 + 熔断（已有采集，加阈值即可）> 4.5 / 4.6 / 4.7 守护类。

5. 核心洞察

💡 OpenClaw + 飞书 = 你能"跟 agent 聊天"，但无法"管理 agent 工作"

pocketctl 的价值不在于"发消息"（飞书已经做了），而在于 agent 跑起来之后的完整生命周期管理——实时监控、审批、控制、分析。

6. 推荐接入方向

pocketctl 作为 OpenClaw 的"控制塔"

不做消息入口，做 agent 运行时的监控审批层。

典型工作流

📱 飞书 → 🦞 OpenClaw Gateway
接收消息 + 编排 agent → 🤖 Claude Code
+ Codex
执行 coding 任务 → 🖥️ pocketctl Daemon
深度监控 + 审批代理 → 📱 iOS App / Web
实时查看 · 审批 · 控制
环节谁来做为什么
发起任务 OpenClaw + 飞书 飞书是多通道中最自然的入口，OpenClaw 负责路由和编排
Agent 编排 OpenClaw 多 agent 协作是 OpenClaw 的原生能力
实时流监控 pocketctl JSONL 深度解析、sub-agent 追踪、实时时间线
Tool 审批 pocketctl PreToolUse hook + 审批卡片，飞书无法实现
Session 控制 pocketctl PTY 操控（/compact、/effort、中断、切模式）
Token 分析 pocketctl 多维度聚合、历史趋势
