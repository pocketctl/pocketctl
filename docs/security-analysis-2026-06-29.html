一、架构概览

[Daemon (Go)]  ←──wss://──→  [Nginx 443 TLS]  ──proxy──→  [Relay (Fastify) :8080]  ──→  [PostgreSQL :5432]
   ↕                              HTTP/301→HTTPS              ↕ JWT auth
[本地 agent (claude/codex)]                                  [Web/iOS client WS]

生产部署形态（docker-compose.prod.yml）：仅 Nginx 对外暴露 80/443，Relay(8080) 和 PostgreSQL(5432) 均 expose（容器内部），不发布端口。

二、网络穿透风险评估 🟢 低风险

已有的防护（强项）

  1. 默认走公网中转，不是直连穿透。Daemon 连接公共 relay wss://www.pocketctl.me/ws（internal/i18n/messages.go:39），架构上是"客户端→中继服务器→客户端"模型，relay 本身不主动反向打洞到内网 daemon。不存在服务端向内网建立反向通道。
  2. 数据库不对外暴露。docker-compose.prod.yml:19 postgres 仅 expose: 5432，只有同网络的 relay 容器可达。
  3. Relay 不对外暴露。docker-compose.prod.yml:37 relay 仅 expose: 8080，所有外部流量必须经 Nginx。
  4. Nginx 禁止访问隐藏文件（deploy/nginx/pocketctl.conf:90）。

需关注（非高危）

  • --relay / POCKETCTL_RELAY_URL 可指向任意服务器（messages.go:40-48）。设计特性（自托管），但若用户被诱导设置恶意 relay URL，daemon 会主动连过去。属用户配置风险。
  • approval hook 是本地 Unix socket（main.go:784），不跨网络，无穿透面。

三、Daemon↔Relay 连接劫持风险评估 ⚠️ 中低风险

已有的防护（强项）

  1. 生产强制 TLS。Nginx 配置 TLSv1.2 TLSv1.3 + HSTS max-age=31536000，HTTP→HTTPS 301（pocketctl.conf:11-16,27）。Daemon 默认用 wss://。
  2. TLS 证书校验未禁用。Go 端用 websocket.DefaultDialer.DialContext（ws/client.go:193）和 http.DefaultClient（api/client.go:232），全局无 InsecureSkipVerify。MITM 需持有受信证书。
  3. WS 连接强制鉴权。relay 的 /ws 端点（server.ts:1058-1075）：无 token 或 API key 立即 socket.close(4001)。
  4. JWT 签名验证 + 吊销检查。WS 用 verifyAccessTokenWithRevocation（server.ts:1060）；refresh token 有轮换 + 重用检测（breach detection 会吊销该用户全部 token）。

劫持/冒充风险点（中低危）

#风险点代码位置说明
1JWT 在 URL query 传递ws/client.go:188token 进 URL，会进入 Nginx access log、浏览器历史/referrer。服务端日志泄露 = token 泄露。建议改用 Sec-WebSocket-Protocol 子协议或首帧鉴权。
2REST verifyAccessToken 不查吊销auth.ts:61只有 WS 和 refresh 走吊销检查；普通 REST 不查 jti 黑名单。已吊销的 access token 在 24h 过期前仍能用。
3sameUser(null,null)=truerouter.ts:905-907两个 userId 都为 null 时被视为同用户。匿名 daemon 与匿名 client 互通，存在跨用户广播的理论窗口。
4CORS origin: true 兜底server.ts:64ALLOWED_ORIGINS 未配置时允许所有来源跨域。WS 不受 CORS 限制，但 REST 端点会被任意网站脚本调用。
5API key 明文比较server.ts:1069非常量时间比较；API key 匿名连接能力受限。低危。
6无 daemon 身份绑定校验router.ts:45daemon_id 由客户端自报，relay 不校验其是否真属于该机器。拿到他人 token 即可用任意 daemon_id 注册并接收其 session 流。
综合：外网链路上劫持需打破 TLS（很难），传输层劫持风险低。真正风险是令牌泄露后的身份冒充（#1 日志泄露 + #2 吊销失效 + #6 无设备绑定）。

四、数据泄露风险

🔴 严重 — replay 历史回放无授权校验（IDOR / 越权读取）

位置：relay/src/router.ts:564 → handleReplay（717-762 行）

handleReplay 内部没有任何 isSessionOwnedByUser / sameUser 校验，直接 getEventsAfter(sessionId) 把该 session 的全部事件 payload 发给请求方。含完整对话：user_text、agent_text、tool_call.input（常含代码/命令）、tool_result.output（命令执行结果）。

  • 利用前提：攻击者是已认证用户（任意账号），知道目标 session_id。
  • session_id 是 UUID v4（manager.go:726），盲猜不可行；但存在多条泄露途径（日志、URL 分享、其他越权接口枚举）。
  • 对比：REST /api/sessions/:id/export（server.ts:490）做了 isSessionOwnedByUser 校验，而 WS replay 没有——同一份数据，REST 把关、WS 放行，明显疏漏。

🔴 严重 — 通用 client→daemon 路由无 session 属主校验

位置：router.ts:683-714

凡带 msg.session_id 且未被前面分支显式拦截的命令，都走这段通用路由：仅查 session 归属哪个 daemon，不校验该 session/daemon 是否属于当前 client。受影响的破坏性/注入性命令：

命令daemon 端行为危害
user_message注入内容到他人 PTY向受害者会话注入任意 prompt，诱导执行恶意操作（"请把 .env 内容打印出来"）
session_killKillSession远程杀掉他人正在运行的会话
session_interruptInterruptSession中断他人进行中的任务
set_permission_modeSetPermissionMode把他人会话切到 bypassPermissions，令其 agent 无确认执行危险工具
set_effort注入 /effort干扰他人会话

唯一做了属主校验的只有 session_delete、session_pin、daemon_restart、list_models、session_create。根因：WS 命令面太宽，授权分散在各 case 手工补，通用分支成了兜底漏洞。

🟠 高 — listSessions（无 userId）返回全库会话

位置：db.ts:295 + router.ts:769

当 client 的 userId === null（API key 登录，server.ts:1069 设 null）时，handleListSessions 走 listSessions 分支，SQL 无 user_id 过滤，返回所有用户的所有会话标题、daemon_id、hostname、cwd。结合上面的 replay 越权，等于一条完整泄露链：用 API key 拿到全部 session_id → 逐个 replay 取全文。

🟠 高 — removeDevice 不校验属主

位置：db.ts:607 + REST DELETE /api/devices/:token（server.ts:306）

export async function removeDevice(pool, deviceToken) {
  await pool.query(`DELETE FROM devices WHERE device_token = $1`, [deviceToken]);
}

任意已认证用户，知道他人的 deviceToken 即可删除其推送设备。危害是拒绝服务：受害者收不到离线/会话完成推送。

🟡 中 — JWT 走 URL query 进服务端日志

位置：ws/client.go:188 + nginx access_log（pocketctl.conf:42）。WS token 在 ?token= 中，nginx 默认记录完整 $request_uri。access log 泄露 = 泄露 24h 有效 token。REST 用 Authorization header（不走日志），WS 没有。

🟡 中 — REST access token 不查吊销

位置：auth.ts:61 verifyAccessToken（无 revocation）vs verifyAccessTokenWithRevocation（80）。REST handlers 全部用前者，不查 jti 黑名单。forceKick 吊销的 token 在 24h 内仍可读用户数据。

五、数据删除/破坏风险

🔴 严重 — user_message + set_permission_mode = 远程代码执行前置链

这是最危险的破坏面：攻击者通过通用路由越权（见第四节）向他人生会话：

  1. set_permission_mode → bypassPermissions
  2. user_message → 注入 prompt 让 agent 执行 rm -rf、git push --force、读取并外传密钥等

agent 在受害者机器上以用户完整权限运行（daemon 启动 agent 不做沙箱），bypassPermissions 下无确认。等同于通过 relay 远程操控他人电脑。这是把"数据删除"风险推到最高的一条路径。

🟢 安全 — session_delete 有属主校验

位置：router.ts:597，有 isSessionOwnedByUser 校验 ✅。删会话前校验属主，失败返回 error。但注意它物理删除 events（真删，非软删），删后无法恢复。

🟢 安全 — deleteDaemon 有属主校验

位置：db.ts:218，有 user_id = $2 属主校验 ✅。会把该 daemon 的 sessions 的 daemon_id 置 NULL（不删会话数据），属设计行为。

🟡 中 — cleanStaleSessions 自动改状态

位置：db.ts:341。daemon 离线 >5 分钟，relay 自动把其 running/busy 会话改为 completed。不删数据，但会造成状态错乱（会话实际还在 agent 端运行，relay 侧已显示结束）。

🟡 中 — forceKick 可吊销他人全部 token

位置：router.ts:882 revokeToken(pool, '', userId, 'force_kick')。若空 jti 会吊销该 userId 的全部 token，被盗 token 的攻击者可对受害者发起"吊销全部会话"的 DoS。已有"每小时 3 次"限流缓解。

六、数据丢失风险评估 ⚠️ 中风险

已有的防护（强项）

  1. 事件幂等去重。insertEvent（db.ts:252）用 event_hash + ON CONFLICT DO NOTHING。
  2. 会话路由重建。relay 重启后 rebuildSessionRoutes 从 DB 重建映射，历史会话不变孤儿。
  3. 僵尸会话对账。reconcileDaemonSessions 把僵死的 running/busy 行标 completed。
  4. 优雅关停。SIGTERM 先 broadcastRelayRestarting 提示 daemon 重连。
  5. token 统计永久保留。deleteSession 先把当日用量补偿进 token_daily_stats 再删事件。

丢失风险点（中危）

#场景代码证据影响

关键结论：在 relay↔DB 瞬时故障（#1）和 daemon↔relay 长断网（#2）两个场景下，存在静默丢消息的真实窗口。其中 #1（fire-and-forget 写库）是最隐蔽的——日志里看不到失败、客户端却丢数据。

八、修复优先级建议

仅建议，未改动任何代码。

第一优先（堵越权 — 收益最高）

在 handleClientMessage 入口对所有带 session_id 的命令统一做 isSessionOwnedByUser 校验；handleReplay 开头加同样的 owner 检查；removeDevice 加 user_id 条件。这一类是"在 router 里加几行 sameUser/owned 判断"，收益最高。

第二优先（缩小泄露面）

listSessions 的 null 分支要么删除（禁止匿名 list），要么仅返回摘要不返回 session_id/hostname/cwd。

第三优先（令牌安全）

WS token 改用 Sec-WebSocket-Protocol 子协议或鉴权首帧，移出 URL；REST 统一用 verifyAccessTokenWithRevocation。

第四优先（数据韧性）

编排层加定时 pg_dump + 异地存储；考虑 session 软删除（deleted_at）而非物理删，配合备份做可恢复。daemon 端可为 outputCh 增加本地磁盘 spool，重连后回放。

九、总体结论

网络穿透

🟢 低

纯出站中继模型，DB/Relay 不对外暴露，无反向打洞。

连接劫持（传输层）

🟢 低

生产强制 TLS1.2/1.3 + HSTS，证书校验未绕过，MITM 难度高。

身份冒充（令牌层）

🟡 中

JWT 走 URL、REST 不查吊销、daemon_id 无设备绑定。

数据泄露（越权层）

🔴 严重

WS replay 与通用命令路由缺属主校验，注册账号即可越权读全对话、控制他人会话。

数据删除/破坏

🔴 严重

越权 user_message + set_permission_mode 构成 RCE 前置链，可远程操控受害者机器。

数据丢失

🟡 中

fire-and-forget 写库 + daemon 无磁盘缓冲 + 90 天硬删 + 无备份，断网/崩溃下静默丢消息。

最关键结论：当前代码在 WS 命令面的授权是不完整的——REST 接口普遍有属主校验，但 WS 的 replay 和通用 client→daemon 路由存在系统性缺口。一个注册账号（甚至 API key 匿名连接）即可越权读取他人完整对话、向他人会话注入内容、切换权限模式，这是比"传输劫持"更现实的攻击路径，建议优先处理。
